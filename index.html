PATH 02 · DEEP DIVE

RBAC 與權限範圍Role assignments and scope

RBAC 不只是選一個角色；你同時決定「誰」可以做「什麼」，以及權限套用「在哪裡」。

01

安全性主體 WHO

被授權的身分，例如使用者、群組、服務主體或受控識別。

The identity receiving access: a user, group, service principal, or managed identity.

PRINCIPAL
02

角色定義 WHAT

一組允許的操作。Reader 可檢視資源；Contributor 可管理資源，但不能指派 Azure RBAC 角色。

A set of allowed actions. Reader can view resources; Contributor can manage resources but cannot assign Azure RBAC roles.

ROLE
03

範圍 WHERE

角色生效的資源邊界。由管理群組、訂用帳戶、資源群組到個別資源，子範圍會繼承上層指派。

The boundary where the role applies. Child scopes inherit assignments from management groups, subscriptions, resource groups, and resources.

SCOPE

SCOPE HIERARCHY

範圍越上層，
影響越廣。

在上層範圍授予的權限會向下繼承。只想管理一個資源群組，就不必把角色指派在整個訂用帳戶。

Assignments flow down to child scopes. If access is needed for one resource group, there is no need to grant it at the subscription level.

考點辨析　Azure RBAC 管理「誰能對 Azure 資源做什麼」；Azure Policy 管理資源應符合的規則與設定。兩者目的不同。

Exam distinction　Azure RBAC controls who can do what to Azure resources. Azure Policy enforces rules and configuration requirements. They solve different problems.
